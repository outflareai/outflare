# Agent memory and self-discovery

Outflare is used through many clients at once: Claude Desktop, ChatGPT, Cursor and other MCP clients, the CLI, the dashboard, and agents running missions. None of them share memory, and a chat forgets everything when it ends. So Outflare keeps what is worth remembering, and every client reads it with one call.

## What Outflare stores, and what it doesn't

Outflare remembers the business, not the conversation.

| Kept in Outflare (shared, lasting) | Kept by the client (this chat only) |
| --- | --- |
| Each brand's context ("About your company"): name, website, what it does, audience, goals, voice, rules, notes | The conversation and its reasoning |
| Memories: one-line preferences, decisions, facts and feedback | Drafts not accepted yet |
| Brand context: offer, audience, voice; ideal customer profiles | Which calls it made and why |
| Findings: what was learned about a brand's marketing, with evidence, confidence, scope and a review date | |
| [Knowledge](knowledge.md): articles and quick answers the team wrote | |
| What happened: audit log, events feed, missions and their calls | Plans for this session |

Chat transcripts are never stored: the client keeps them, they are large and sensitive, and little in them is worth reusing. What is worth reusing the agent distills into a memory, tells the person in one line, and the person can correct or forget it on the Company page.

Memories are data agents read, never instructions that change what runs. Limits, scopes, mission gates and the send policy decide that.

## The pieces

- **Brand context** (`GET`/`PATCH /v1/workspaces/{ws}/context?brand=`, and `.../brands/{brand}/context`; tables `brands` and `brand_context`): brands are fully separate, so each brand has its own versioned context ("About your company": about, audience, goals, voice, rules, notes, with its name, website, logo and colours on the brand) and none is shared. Its **business details** (`legal_name`, `tax_id` and a postal `address` in the same shape as a record's location attribute, migration 0527; `address_text` is it on one line) are entered there once and reused: lifecycle email footers and the `{{brand_address}}` and `{{brand_legal_name}}` variables (sequences too), the brand's help centre footer and Organization markup, its cookie policy ("This site is run by…") and the Markdown agents read. Without `brand`, the context routes read and edit the workspace's first brand's (or the one brand a token is kept to). `missing` lists the onboarding fields still empty (about, goals, voice); `ask_for_missing` turns false when they are filled or a person dismisses the question (`onboarding_dismissed: true`). The GET also returns the brand's pinned and recent memories with those no brand has, the other brands in a line each, and a Markdown version for a prompt. Each brand started from a copy of the workspace's old company context (migration 0470), which nothing reads any more. Each brand also has its **knowledge**: what its website says it offers (a summary, the industry, and bullets for products, services, features, integrations, capabilities, who it serves and use cases, each with the page it came from), read through the workspace's own page reader (Geonode) and written by its own AI model (the Brand knowledge task) when a brand is created with a website or on `POST .../brands/{brand}/knowledge/read`, then edited by people (`PUT .../knowledge`). A read fills in `about` and `audience` only when they are empty. AI visibility drafts its questions from it.
  - **The knowledge sheet, reviewed.** Paid ads are written only from the knowledge, so it is also a sheet a person signs off. `GET /v1/brands/{brand}/knowledge` returns it with how it stands, and the brand's context carries the same (`knowledge_reviewed_at`, `knowledge_reviewed_by`, `knowledge_changed_since_review`, `knowledge_refresh_daily`, `knowledge_trusted`). A person (their own session, `context.manage`) marks it reviewed with `POST /v1/brands/{brand}/knowledge/review` (MCP `review_brand_knowledge`; audit `brand.knowledge_reviewed`); an agent or API token gets 403, because agents write ads from the sheet and never sign it off. **The read never fails silently**: a brand created or asked to read without a page reader records `knowledge_error` `connector_needed`, a read without a usable AI model records `ai_model_needed` or `ai_budget_reached`, and every failure is a `brand.knowledge_read_failed` event with the code (metric `outflare_brand_knowledge_reads_total`). **Daily refresh**: once an ad account is connected to the brand, `knowledge_refresh_daily` turns on and the website is read again every day (job `brand.read_knowledge`, queued by the hourly sweep); a read that changes the brand's products, services, prices or summary sets `knowledge_changed_at` and clears the review so the owner looks again. The status blocker `ads_knowledge_unreviewed` (area `ads`, a person's fix) lists brands with an ad account whose sheet is unreviewed, changed since the review, or whose last read failed; the ads draft writer refuses with 422 `knowledge_unreviewed` until it is trusted ([paid-media.md](paid-media.md), "New ads").
- **Memories** (`/v1/brands/{brand}/memories`, table `memories`): up to 500 characters each, `kind` preference, decision, fact or feedback, optional `brand_id`, `pinned`, who saved it and the mission it came from. Saving the same text twice keeps one. At most 1000 per workspace. Brands share no memories: one saved without a brand is the route's or the workspace's first brand's. Brand tokens see only their own brand's.
- **Findings** (`/v1/brands/{brand}/findings`, table `brand_findings`): what an agent or a person learned about a brand's marketing ("Comparison pages convert search visitors twice as well as guides"), each with its `evidence` (at least one metric, action, experiment or observation, with a note saying what it showed), `confidence` (low, medium, high), `scope` (channel, audience, objective, each optional) and `review_at` (90 days by default). They are the third kind of memory the brand agent plan keeps apart from facts and operational state: learnings, scoped so they inform the next decision without being over-generalised. A finding past its review date is `due`, listed with `?due=true` for an agent to check before trusting; `PATCH` moves `review_at` forward after a review, corrects it, or retires it (`status: retired`, `retired_reason`), and retired findings are kept. `GET /brands/{brand}/context` carries the active ones nearest their review date (at most 20), so an agent that reads the brand reads what was learned. A brand keeps at most 500 active findings. Findings are data, never instructions.
- **Status** (`GET /v1/workspaces/{ws}/status`): blockers worst first, each with a stable `code`, `severity`, `count`, up to five `items`, a `detail` and a `fix` naming the MCP tool, the dashboard page and who must act (`agent` or `person`). Plus `can_send`, a set-up checklist and a one-line `summary`. Home's **Needs you** list shows the same blockers. It is the one to-do list for every module: mailboxes, domains, servers, connections, missions, sending, the fixes list, the inbox, analytics, lifecycle email (`email_domain_failed`, `email_broadcast_failed`), social drafts waiting for approval (`social_drafts_waiting`) and customer data (`duplicates_waiting`, `event_names_to_check`, `events_quarantined`, `crm_import_failed`). A new module that finds work for people adds a blocker here (or fixes on the fixes list), never a list of its own.
- **Scopes**: reading needs `workspace.read`; editing context, memories and findings needs `context.manage`, which "Can make changes" on API tokens and the operator role include.
- **Events**: changes record `context.updated`, `brand.context_updated`, `memory.created`, `memory.updated`, `memory.deleted`, `finding.recorded`, `finding.updated` and `finding.retired` in the audit log, in the same transaction.

## How each client uses it

- **MCP clients**: the server instructions tell the agent to call `get_context` first (with `brand` when the work is for one brand; `OUTFLARE_BRAND` sets a default). It returns the context, memories, brands and status in one answer. If `ask_for_missing` is true the agent asks for the missing fields in one message (or offers to read the website) and saves them with `update_context`. When the person states something lasting, the agent calls `remember`. The `set_up_outflare` prompt runs onboarding; `whats_blocked` walks the status.
- **Built-in mission agent**: the mission check-in (`GET /missions/{id}`) includes `company` with the context and pinned memories, and its system prompt tells it to write in the company's voice, within its rules, and to save memories.
- **Dashboard**: Company → About your company edits the context and lists memories (pin, edit, change kind, forget). Home's set-up card starts with it.
- **CLI and scripts**: `outflare get-context`, `outflare get-status`, `outflare create-memory --text "..."` and the rest come from the OpenAPI document like every other command.

## Errors an agent can act on

The MCP server turns every API error into a first line (`409 conflict: ... (request req_...)`), a `Next step:` line, and `structuredContent.error` with `status`, `code`, `param`, `message`, `request_id`, `retry` and `next_step`. Next steps are keyed by error code in `mcp/src/server.ts` (`nextStep`). When you add an error code to `engine/internal/api/errorcodes.go`, add its next step there if an agent should do something specific.
