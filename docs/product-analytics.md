# Product analytics

Off unless you turn it on. You can keep usage events in a workspace on your own server, send them to **your own** PostHog project, or both, so you can see how people and their agents use Outflare on your server: which features they use, which calls and tools fail and why, where they get stuck, and session replays. This is separate from the [anonymous usage report](telemetry.md), which goes to the Outflare project and never includes people or content.

## Turn it on

| Variable | Default | What it does |
| --- | --- | --- |
| `OUTFLARE_POSTHOG_KEY` | none | Your PostHog **project** key (`phc_...`, under Project settings). A personal API key (`phx_...`) is refused. |
| `OUTFLARE_POSTHOG_HOST` | `https://us.i.posthog.com` | Where events go. `https://eu.i.posthog.com` for EU Cloud, or your self-hosted PostHog's address. |

In Docker Compose, add them to `deploy/.env` and restart. `GET /v1/meta` then includes `product_analytics`, and the web app loads PostHog the first time it opens.

### Keep them in a workspace

| Variable | Default | What it does |
| --- | --- | --- |
| `OUTFLARE_EVENTS_WORKSPACE` | none | The id of a workspace on this server that keeps the server's events as [product events](customers.md#product-events), such as one you made for your own team. Every action and error is kept; successful API and MCP calls (`api.called`) are kept once an hour per person, since the request logs (Logs in the app) have each one. |
| `OUTFLARE_EVENTS_BRAND` | the first brand | The brand in that workspace the events are stored under, by id or handle: the one whose [website tracking](website-tracking.md) tag is on your own site, so each person joins the visits they made before signing in. Any call a signed-in person makes from a browser carrying the tag's cookie joins them, not only signing in. |

Each event is stored as a `track` call with source `outflare`, under the same name and properties as below. The people who use your server become customer records in that workspace, identified once by their account's email (verified once they confirmed it) and name, so the workspace's analytics, segments and lifecycle email work on them. Work with no person behind it waits unmatched on an `anonymousId` such as `workspace:<id>`. Outflare names these events itself, so they arrive approved in the catalog. Storing them records no events of its own.

If your own website runs the [website script](website-tracking.md) with a site key in that same workspace, a person who signs up or signs in from a browser that visited it is joined to those visits: the server reads the script's `of_aid` cookie (it sits on the widest domain the site allows, so `www.` and `app.` share it) and sends it with the person's `identify`. Their earlier visits, and the ad click ids on them, join their record, so [attribution](attribution.md) credits the sign-up and later payments to the click, and [conversions sent back](paid-media.md#sending-conversions-back) to the ad platform carry it. The cookie exists only when the visitor's consent lets the script keep its id. It is never sent to PostHog. Anyone with `customers.read` in that workspace can read them, so keep its members to your own staff. The web app's own page views and clicks still go only to PostHog for now.

## Events

The server records every action, whoever takes it (the web app, an API token, the MCP server, the CLI, a job), and every error. The web app adds what only the browser sees. Every event has:

| Property | What it is |
| --- | --- |
| `distinct_id` | The person's Outflare user id, also for calls with an API token they made. Work with no person behind it (a system job) creates no person in PostHog. |
| `workspace_id` | The workspace, also as the PostHog group `workspace`. |
| `outcome` | `success`, `failure` (refused: bad input, no permission, a limit, not found) or `error` (broken: a bug, a provider or database failure). |
| `error_code` | When it isn't a success: the API's error code (`GET /v1/error-codes`), or the reason a job or sign-in failed. |
| `surface` | `web`, `api`, `mcp`, `cli`, `sdk`, `job`, `mission`, `agent` (an extension's loop calling in process, or a held change a person approved replaying) or `system`. |
| `actor_type`, `request_id` | Who acted (`human`, `api_token`, `agent`, `system`) and the request, to find it in the server log. |

Event properties carry ids, codes, counts and durations only: never names, email addresses, domains, message content or error text. The server log has the full error next to the same `request_id`, and every event at debug level.

## How it works

- The server sends its events to `OUTFLARE_POSTHOG_HOST` in batches every few seconds, in the background: a slow or unreachable PostHog never slows a request, and events are dropped rather than queued without limit.
- The browser sends everything to `/ingest/` on your own server, which forwards it to PostHog. Ad blockers don't drop it, and no request leaves your domain from the browser. The proxy strips your session cookie and API tokens before forwarding.
- Signed-in people are identified by their Outflare user id, email and name (set once on the PostHog person, never on events), and grouped by workspace, so you can see usage per account.
- Clients name themselves in an `Outflare-Client` header (`web`, `mcp/0.1.0`, `sdk-ts/0.1.0`; the SDK's `clientName` option sets it). The MCP server also sends `Outflare-Tool` and `Outflare-Agent`. Only names, never arguments.
- Customer data stays out. Autocapture and session replay mask all page text, inputs and element attributes. URLs keep only the page (`/:ws/sequences/:item`), never workspace names or ids, domains, lead or sequence ids, invite tokens or query strings (UTM tags are kept).
- Signing out resets the PostHog identity, so the next person on that browser starts fresh.

Cookies: PostHog stores an anonymous id in a first-party cookie on your domain. If your visitors are in the EU or UK and you treat that as needing consent, put the app behind your own consent banner or leave this off.
